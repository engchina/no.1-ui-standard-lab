# レイアウトリージョンのコントラクト

## 意図

ページや区切られた作業領域には、プロダクトのコンテンツを追加する前の段階で、予測可能な構造上のリージョンがあるべきである。ビルダーは、汎用の Section、5 スロットの Layout プリミティブ、またはコンテキストに応じた Toolbar を使える。これにより、各サーフェスがインセット、境界、リージョンの方向、コンテンツの所有権を個別に作り込む必要がなくなる。これらの下位リージョンとアプリケーションナビゲーションを組み合わせたページシェルは、AppShell が所有する。

## メンバーシップルール

主な公開目的が安定した構造リージョンの定義であるコンポーネントは、このファミリーに属する。ここでいう構造リージョンとは、汎用的なページ／コンテンツリージョン、Layout の 5 スロットトポロジー内の名前付き位置、またはコンテキストアクションリージョンのいずれかである。メンバーは共有のレイアウトプリミティブを組み合わせて構成してもよい。ただし、任意の子要素を並べるだけのものより強い境界を所有する。

- **メンバー:** Section、Layout とその Header・Content・Footer・Panel の各リージョン、Toolbar。
- **協力者:**
  - `family:layout-primitives` は、任意の子要素を配置するユーティリティを提供する。
  - `architecture:container-padding` は、Section、Layout とその各リージョン、Table、Toolbar、Divider が使う、より広範なインセットおよびブリードの仕組みを提供する。
  - useResizable と ResizeHandle は、パネルのサイズを制御できる。
  - AppShell はページシェルを所有し、Layout とアプリケーションナビゲーションを組み合わせる。
  - コンポーネントのテーマ設定は、ビジュアルのターゲットを所有する。
- **対象外:**
  - Stack、Grid、Center とそれらのモディファイアは、構造リージョンを主張せずに任意の子要素を配置する。
  - FormLayout は、フィールド固有の配置と任意入力の扱いを所有する。
  - Card は、個別アイテムのためのサーフェスである。
  - AppShell は、この再利用可能なリージョン文法ではなく、ページシェルとナビゲーションのセマンティクスを所有する。
  - Table は構造化データを、Divider は区切りを所有する。どちらも `architecture:container-padding` に参加しているが、それだけでレイアウトリージョンのメンバーになるわけではない。

flex の行、パディング付きのラッパー、ヘッダー風の見た目を描画しているというだけでは、コンポーネントはこのファミリーに加わらない。

## 共有オーナー

- Section は、汎用的な塗りつぶし付きのページ／コンテンツリージョンを所有する。これには、バリアント、選択されたディバイダーの辺、コンポーネントのパディング、ネストされた Section の挙動が含まれる。
- Layout は、5 スロットのトポロジー、スロットの有無、リージョンの位置、共有の外側／内側インセット、高さモード、コンテンツ幅の伝播、ヘッダー／フッターのディバイダーのデフォルトコンテキストを所有する。ページシェルは所有しない。
- LayoutHeader、LayoutContent、LayoutFooter、LayoutPanel は、それぞれのリージョン要素、任意のランドマークの role／name、ローカルのパディング、リージョン固有のサイズやスクロールの挙動を所有する。
- Toolbar は、コンテキストアクションリージョンを所有する。これには、start／center／end のレーン、ツールバーのセマンティクス、キーボードによる移動、サイズのカスケードが含まれる。塗りつぶしのサーフェス、バリアント、選択されたディバイダーの辺は Section に委譲する。
- `architecture:container-padding` は、継承されるインセットとブリードの仕組みを所有する。
- useResizable と ResizeHandle は、リサイズの状態とインタラクションを所有する。LayoutPanel は、それらが示す現在のサイズを幅の代替オーナーとして受け入れる。また、折りたたみ時と展開時の端からの表示処理のために、自身の要素をリサイズコントローラーに提供する。折りたたまれるパネルのフォーカス移動と inert 状態は LayoutPanel が所有する（`component:LayoutPanel` FR7、AR2）。

## コンポーネント横断の不変条件

- **FR1 — リージョンが所有するのは構造であり、プロダクト上の意味ではない。** メンバーは空間的な境界を確立し、呼び出し側のコンテンツを描画する。ただし、そのコンテンツのプロダクトセマンティクス、状態、コンポーネントコントラクトは引き受けない。唯一の例外は、Toolbar が配下のボタン全体で行う押下トラッキング（`family:action-groups` FR5）である。
- **FR2 — リージョンの方向は論理的である。** start と end は書字方向に従う。ディバイダーの配置とパネルの隣接関係も、同じ論理的なリージョン位置を使う。
- **FR3 — Layout はスロットの有無からジオメトリを選択する。**
  - Header、Content、Footer、Panel は、Layout の境界に接する箇所には外側インセットを、他のリージョンと接する箇所には内側インセットを適用する。
  - LayoutContent は、自身のルートをスクロール、パディング、直接の子要素のオーナーとして保つ。
  - 省略されたスロットは、領域のラッパーを残さない。
  - 各リージョンは、自身が適用するジオメトリを全幅（フルブリード）の子孫要素に向けて再公開する（`architecture:container-padding` INV2）。
- **FR4 — 明示的なリージョンパディングは、自動で適用されるインセットを置き換える。**
  - Section は、自身のコンポーネントインセットを公開する。
  - Layout は、外側インセットと内側インセットを名前付きスロットに分配する。
  - リージョンで明示的なパディングまたはゼロパディングの経路を使うと、ローカルのスタイルが選択される。
  - 自動で設定された Layout の端は、適用したパディングを再公開する。例外は LayoutContent のコンテンツ幅用ガターである（`component:LayoutContent` FR2）。
- **FR5 — 構成上オーナーが 2 つになり得る場合、境界の所有は呼び出し側が選択する。**
  - LayoutHeader と LayoutFooter は、それぞれ暗黙の辺を所有する。
  - Section と Toolbar は、選択された辺を公開する。
  - LayoutPanel はコンテンツ側の辺に線を描画でき、ResizeHandle も同じ辺に描画できる。現在のコードでは、両方が描画することを防いでいない。
  - そのため、リサイズ可能なパネルの構成で隣接する ResizeHandle がディバイダーを所有する場合は、`LayoutPanel hasDivider={false}` を設定しなければならない。
- **FR6 — ディバイダーの有無はスペーシングを変えることがある。** 現在の Layout リージョンでは、header、footer、panel のディバイダーがない場合、それに伴う内部のスペーシングを詰める。明示的なディバイダーがある場合は、区切られた境界が維持される。
- **FR7 — スクロールは明示的かつローカルである。**
  - LayoutContent と LayoutPanel は、現在の `isScrollable` の挙動を所有する。
  - Section と Toolbar は、ファミリーに属しているというだけでスクロールコンテナにはならない。
  - Layout の `height="fill"` はリージョンのスクロールを内部に収める。`height="auto"` では、それを含むページが伸長する。
- **FR8 — ランドマークのセマンティクスは明示的なままである。** 名前付きの見た目上の配置によって、`banner`、`main`、`navigation`、`complementary`、`contentinfo` が自動的に割り当てられることはない。呼び出し側が、コンテキストに応じてサポートされている role とラベルを指定する。
- **FR9 — レスポンシブな置き換えは自動では行われない。**
  - Section と Toolbar は、現在の表示を維持する。
  - Layout は、呼び出し側から渡されたリージョンを描画する。
  - 狭い幅でリージョンを省略するか置き換えるかは、AppShell、プロダクト側の構成、または他のコンポーネント固有のオーナーが決定する。
  - AppShell は、モバイルのブレークポイントをまたぐ際もメインコンテンツをマウントしたまま保つ（状態は保持される）。
- **FR10 — リサイズの所有は委譲されたままである。** `resizable` を指定した LayoutPanel は、`width` prop の代わりにフックから提供される現在のサイズを使う。リージョンファミリーは、スナップ、永続化、折りたたみ、キーボード、ポインターの挙動を再定義しない。
- **FR11 — テーマ設定はコンポーネントが所有したままである。**
  - 構造上のメンバーシップによって、ファミリー単位のターゲットが作られることはない。
  - 現在の `.doc.mjs` メタデータが出荷済みのターゲットと機能を文書化し、ランタイムの `themeProps()` がそれらを出力する。コンポーネント横断のルールは `architecture:component-theming-surface` が所有する。
  - コンポーネント仕様では、アナトミーのマッピングが存在する場合に、任意のメタデータとして追加できる。
- **FR12 — コンテンツ幅を指定しても、スクロールバーは開いている側のコンテンツ端に置かれる。**
  - パネルなしで `contentWidth` を設定すると、LayoutContent は利用可能な中央領域全体に広がり、コンテキストに応じたインライン方向のインセットによって直接の子要素を揃える。
  - パネルがちょうど 1 つの場合、そのパネルは中央寄せされたフレームに揃ったままになり、LayoutContent は反対側の開いている側まで広がる。start／end を反転したケースにも同じルールが適用される。
  - パネルが両側にある場合は、中央の構成全体が制約されたままになる。
  - パーセンテージ値、固有幅の値、裸の CSS 変数は、1 つの揃え基準を安全に共有できない。そのため、これらを使う場合も制約された構成のままになる。長さの値を持つ変数を明示的に使う経路は `calc(var(...))` である。

## 許容されるコンポーネント間の差異

- **AV1 — リージョンの強さ。** Section は汎用リージョン、Layout のメンバーは 5 スロットプリミティブ内の位置を認識するスロット、Toolbar はセマンティックなアクションバーである。
- **AV2 — サーフェスの処理。** Section と Toolbar は、Section のバリアントと選択された辺を使える。Layout のリージョンは、既存のディバイダーとパディングの処理を使う。同じファミリーに属していても、ビジュアル API が統一されるわけではない。
- **AV3 — リージョンのコンテンツ。** header、footer、panel、content、およびツールバーのレーンには、それぞれのコンポーネントコントラクトが許可する任意のコンテンツを入れられる。
- **AV4 — サイズモデル。** Layout は、fill/auto のコンテナ高さとコンテンツ幅の伝播を所有する。個々のリージョンは、該当する高さ、幅、パディング、スクロールの props を所有する。Section は自身のボックスサイズの props を所有する。
- **AV5 — インタラクション。** Toolbar は、ロービングフォーカス、キーボードヒント、および `family:action-groups` FR5 によって与えられる配下のボタン全体での押下トラッキングを所有する。他のメンバーはツールバーの挙動を追加しない。リサイズのインタラクションは Resizable が所有する。
- **AV6 — 構成の仕組み。** メンバーは、Stack のユーティリティ、CSS による直接のレイアウト、コンテキスト、コンポーネントの組み合わせのいずれを使ってもよい。所有するサーフェスは、外から観測できるリージョンのコントラクトである。
- **AV7 — レスポンシブのポリシー。** 呼び出し側は、リージョンを省略、置き換え、または外部から適応させられる。ファミリーとしてはブレークポイントを設定しない。

## 採用状況と例外

| コンポーネントまたは関心事 | 採用状況                                                              | 現状のギャップまたは例外                                                                                                                                                                                                                                                                                                                       |
| -------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Section                    | 汎用リージョンであり、container-padding の公開元                      | ネスト時のはみ出し（エスケープ）は、インライン方向では常に適用されるが、ブロック方向では最初／最後の子要素にのみ適用される                                                                                                                                                                                                                     |
| Layout コンテナ            | スロットコンテキストを持つ 5 スロットのリージョンオーナー             | content のみの LayoutContent は全幅のまま、インセットで直接の子要素を揃える。パネルがちょうど 1 つの場合、パネルは揃えられたまま、コンテンツは反対側の開いている端まで広がる。両側にパネルがある場合や固有のコンテンツ幅の場合は、中央の構成が制約されたままになる。トポロジーはテストでカバーされている。反転時の揃えとスクロールバーの配置はブラウザでのエビデンスでカバーされている。 |
| LayoutContent              | スロットの有無を読み取り、外側／内側インセットを適用する              | 各端は適用したパディングを公開する。端ごとのインセットとその公開については監査時のブラウザ記録しかなく、常時実行されるチェックはない                                                                                                                                                                                                         |
| LayoutPanel                | 位置を認識したパディングを適用し、リサイズ駆動の幅を受け入れられる    | Layout 端の自動パディングでは、内側ジオメトリ変数がベースラインのまま残る。呼び出し側がパネルに `hasDivider={false}` を設定しない限り、隣接する `ResizeHandle hasDivider` によって線が二重になることがある                                                                                                                                  |
| LayoutHeader/Footer        | リージョン固有のインセット、境界、ランドマーク                        | リージョン間で算出スタイルが一致するかどうかは、単一のブラウザマトリクスではカバーされていない                                                                                                                                                                                                                                                 |
| Toolbar                    | Section をベースとしたサーフェスにツールバーの挙動を加えたもの        | インライン方向のインセットと辺の補正は、組み込まれた Section の現在のパディングコンテキストに従う                                                                                                                                                                                                                                             |
| レスポンシブなリージョン   | 呼び出し側／AppShell による構成                                       | LayoutPanel には、現時点で共通のレスポンシブな表示制御のコントラクトがない                                                                                                                                                                                                                                                                     |

これらの行は、出荷済みの挙動と検証上のギャップを記述したものである。ドキュメントのプルリクエストで黙って変更してよい、承認済みの例外ではない。

## 変更の連動

- 構造リージョンのコンポーネントを追加または変更する場合は、メンバーシップを確認する。このコントラクトを更新するのは、共有の境界が変わる場合のみである。
- Layout のスロットの有無、領域コンテキスト、インセットの分配、ディバイダーの継承、高さモード、コンテンツ幅の伝播を変更する場合は、対応するリージョンのテストとブラウザでのエビデンスを更新する。
- Section のパディング、ネスト時のエスケープ、バリアント、ディバイダーの挙動を変更する場合は、そのコンポーネントコントラクトを更新する。継承されるジオメトリが変わる場合は、`architecture:container-padding` もレビューする。
- Toolbar のレーン、セマンティクス、キーボードの挙動、サイズのカスケードの変更は、引き続き Toolbar 側の作業である。Section をベースとしたサーフェスやインセットの関係を変更する場合は、このファミリーと container-padding アーキテクチャもレビューする。
- LayoutPanel のリサイズ統合を変更する場合は、Resizable のコンポーネントコントラクトをレビューする。その際、リサイズの仕組みをこのファミリーに持ち込まない。
- レスポンシブな非表示／入れ替えの挙動を追加するには、コンポーネントまたは上位レベルのオーナーと、互換性のエビデンスが必要である。ファミリーへの所属は、新たなブレークポイント prop を追加する根拠にはならない。

## 決定事項へのリンク

### DEC-1 — 構造リージョンと構成プリミティブは別々のオーナーを持つ

**決定者:** `cixzhang`、`2026-08-30`

Section、Layout とその名前付きリージョン、Toolbar が、レイアウトリージョンのファミリーを構成する。Stack、Grid、Center とそれらのモディファイアは、別のレイアウトプリミティブのオーナーに属する。これにより、共有のリージョンルールは構造上の境界に焦点を絞ったものになり、あらゆる flex/grid コンテナがページリージョンとして扱われることを防げる。

### DEC-2 — ページシェルは AppShell が所有する

**決定者:** `cixzhang`、`2026-08-31`

AppShell は、ページシェルとアプリケーションナビゲーションの構成を所有する。Layout は、ページまたは区切られたコンテナ内で `header`、`start`、`content`、`end`、`footer` の各リージョンを配置するための汎用的な 5 スロットプリミティブである。より広範な container-padding の参加者は、それぞれ自身のコンポーネントの所有権を保持する。

### DEC-3 — content のみの場合の幅の揃えは、コンテンツのスクロールポート内にとどめる

**決定者:** `cixzhang`、`2026-09-09`

パネルなしで `contentWidth` を設定すると、LayoutContent は利用可能な中央領域全体に広がり、コンテキストに応じたインライン方向のインセットによって直接の子要素を揃える。パネルがちょうど 1 つの場合、そのパネルは中央寄せされたフレームに揃ったままになり、LayoutContent は反対側の開いている側まで広がる。論理的な start と end は反転する。

パネルが両側にある場合は、中央の構成全体が制約されたままになる。幅がパーセンテージ指定、固有幅、または未解決の裸の変数であり、1 つの CSS 算術の基準を安全に共有できない場合も同様である。値が長さであることが保証された変数は、`calc(var(...))` を使うことで端でのスクロールを選択できる。
